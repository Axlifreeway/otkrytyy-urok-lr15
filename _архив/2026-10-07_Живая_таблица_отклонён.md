# Открытый урок «Живая таблица»

**ОПЦ.07 Основы проектирования баз данных · ИИ б.9 · по ЛР-15 «Выборка
данных: SELECT, WHERE, ORDER BY» · 90 минут (сокращённая версия на 45 —
в конце)**

Черновик для размышления, 07.10.2026.

---

## 1. Идея в одной фразе

Сначала **группа сама становится таблицей**: у каждого на шее карточка —
строка таблицы `passenger`, и запрос «выполняют» люди: кто подходит под
условие — встаёт, `ORDER BY` — выстраиваются по порядку, `LIMIT 3` —
остаются трое. Потом таблица вырастает до 20 000 строк, людьми её уже не
выполнить — и команды за компьютерами открывают SQL-запросами **настоящие
кодовые замки** на ящике у преподавателя. Ящик открывается, только когда
сняты все замки.

## 2. Почему это удивит, если «Электронная тетрадь» уже была

| Прошлый урок | Этот урок |
|---|---|
| пишешь команду — на экране появляется таблица | **ты сам — строка**, запрос выполняется людьми в аудитории |
| всё происходит на экранах | ключевые моменты — без экранов: встают, выстраиваются, щёлкает замок |
| проверка — сайт сказал «верно» | проверка — **замок открылся или нет**; спорить не с кем |
| гости смотрят | **гости тоже строки**: у комиссии свои карточки, их тоже «выбирают» |

Цифровую тетрадь второй раз не оценят как новинку. А когда завуча
вызывают запросом `WHERE loyalty IS NULL` и он встаёт, это запоминается.

## 3. Что из ЛР-15 урок закрывает

Всё содержание части 2 и 3 работы — но так, что самые «скользкие» места
показываются **телом, а не словами**:

| Средство | Как показывается вживую |
|---|---|
| `SELECT столбцы` | вставшие называют вслух **только** перечисленные столбцы своей карточки; `SELECT *` — читают карточку целиком (и все понимают, почему «звёздочка» плоха) |
| `WHERE =`, `IN`, `BETWEEN`, `LIKE` | встают те, кто подходит |
| `ORDER BY` по двум столбцам | выстраиваются в шеренгу; у кого равный багаж — меняются местами по второму столбцу |
| `DESC`, `LIMIT` | шеренга разворачивается; после третьего — садятся |
| `DISTINCT` | от каждого города выходит один человек |
| **скобки в условии** | два запроса, отличающиеся только скобками, поднимают **разных людей** |
| **`= NULL` и `IS NULL`** | у троих поле «Статус» пустое. Запрос `WHERE loyalty = NULL` — **не встаёт никто**. Пауза. `IS NULL` — встают трое |

Последние две строки — те, на которых студенты ошибаются в работе. Здесь
они увидят ошибку раньше, чем её сделают.

Новых средств сверх ЛР-15 нет: ни соединений, ни `count`, ни группировки
(порядок материала б.9 соблюдён — соединение будет на ЛР-16).

## 4. Реквизит

* **Карточки-бейджи** A6 на шнурке — по числу студентов + 6 для гостей.
  Карточка = строка таблицы `passenger` (вымышленные люди, не данные
  студентов):

  ```
  ┌───────────────────────────────────────┐
  │ passenger                      id 17  │
  │ full_name   Корнилов Глеб            │
  │ city        Тюмень                   │
  │ fare_class  бизнес                   │
  │ baggage_kg  23                       │
  │ birth_year  1998                     │
  │ loyalty     ▢  (пусто)               │
  │ seat        12C                      │
  └───────────────────────────────────────┘
  ```

  Данные подобраны заранее: есть равные `baggage_kg` (для второго столбца
  сортировки), три пустых `loyalty`, повторяющиеся города (для
  `DISTINCT`), имена на одну букву (для `LIKE`). Карточки гостей — с
  «интересными» значениями (пустой статус, самый тяжёлый багаж).
* **Те же строки — в базе** на проекторе: после каждого «живого» запроса
  он выполняется в СУБД, и зал сверяет — совпал ли «человеческий»
  результат с машинным.
* **Ящик** + **блокиратор на несколько замков** (как для LOTO-блокировки
  щитов: одна дужка, 4–6 отверстий под навесные замки) + **4 кодовых
  навесных замка** с перенастраиваемым трёхзначным кодом. Ориентировочно
  2–2,5 тыс. ₽ на всё, реквизит многоразовый.
* **Большая таблица** `passenger` на 20 000 строк на компьютерах
  студентов — генерируется скриптом заранее (тот же формат, что карточки).
* **Конверты с заданиями квеста** — по одному на команду, и конверты с
  подсказками («подсказка стоит минуту»).
* Внутри ящика — **«посадочные талоны»** с именем каждого студента:
  «Рейс: ЛР-15. Выход: ваша собственная база. Вылет: следующая пара»
  (это и есть выдача домашнего задания) + что-нибудь съедобное.

## 5. Ход урока (90 минут)

| Мин. | Этап | Что происходит |
|---|---|---|
| 0–3 | Вход | Карточки уже лежат на местах. Гостям выдаются их карточки на входе: «Сегодня вы — пассажиры». |
| 3–8 | «Вы — таблица» | Тема без объявления: на экране `CREATE TABLE passenger (…)` — столбцы те же, что на карточках. «Каждый из вас — одна строка. Таблица уже в зале». |
| 8–18 | SELECT и WHERE | Преподаватель «выполняет» запросы: `WHERE city = 'Тюмень'` — встают; `SELECT full_name, city` — вставшие называют только имя и город. `IN`, `BETWEEN`, `LIKE 'К%'`. После каждого — тот же запрос на проекторе: совпало ли? |
| 18–26 | ORDER BY, LIMIT, DISTINCT | `ORDER BY baggage_kg DESC, full_name` — шеренга у доски, равный багаж решается фамилией. `LIMIT 3` — остальные садятся. `DISTINCT city` — по одному от города. |
| 26–34 | Две ловушки | **Скобки**: `fare_class = 'бизнес' AND city = 'Тюмень' OR baggage_kg > 25` и тот же со скобками иначе — встают разные люди, зал объясняет почему. **NULL**: `WHERE loyalty = NULL` — тишина, никто не встаёт. «Но у троих же пусто?» → `IS NULL`. |
| 34–42 | «Подними нужных» | Роли меняются: преподаватель называет (или показывает на слайде) **кого** надо поднять — например, «всех, кто родился в 90-х и летит не эконом». Команды на листах пишут запрос; таблица его выполняет; проектор проверяет. Попал ровно в нужных — очко команде. |
| 42–46 | Переход | «А у авиакомпании пассажиров не 30, а 20 000» — на проекторе таблица прокручивается без конца. «Встаньте все, у кого место 12C». Смех. «Вот поэтому есть SQL». За компьютеры. |
| 46–76 | Квест «Пропавший багаж» | Четыре команды, у каждой свой замок и своя цепочка из 3–4 запросов к большой таблице (см. раздел 6). Код замка складывается из ответов. Преподаватель ходит между командами, гости смотрят на ящик. |
| 76–80 | Финал | Последний замок снимается, блокиратор открывается, ящик открыт. Посадочные талоны раздаются — это и есть ДЗ. |
| 80–90 | Рефлексия | «Объясните `WHERE` так, как это чувствует строка таблицы» — по одному предложению от команды. Связь с ЛР-15: на следующей паре то же самое — на своей базе по своему варианту. |

## 6. Квест «Пропавший багаж»

**Легенда.** Рейс Тюмень — Москва. На ленте выдачи остались четыре
чемодана без владельцев; на каждом — повреждённая бирка. Каждая команда
находит владельца своего чемодана. Код замка — из данных найденного
пассажира.

**Устройство цепочки** (у каждой команды своя, по одинаковому шаблону):

1. **Обрывок бирки.** «На бирке читается: начинается на `TJM`,
   заканчивается на `47`». → `WHERE tag LIKE 'TJM%47'` — получается
   несколько строк.
2. **Свидетель.** «Сотрудник помнит: пассажир летел бизнесом или
   комфортом, и чемодан был тяжелее 20 кг». → составное условие.
   **Ловушка скобок**: без скобок `LIKE … AND … OR …` вернёт сотни строк —
   и команда сама вспомнит, что было в «живой» части.
3. **Последний штрих.** «У пассажира не было статуса программы
   лояльности». → `loyalty IS NULL`. **Ловушка NULL**: `= NULL` вернёт
   пустой результат — и команда вспомнит тишину в зале.
4. **Код.** Остаётся одна строка; код замка — номер ряда из `seat` и
   последняя цифра `baggage_kg` (у каждой команды свой рецепт, написан
   в конверте).

Если команда ошиблась — замок просто не откроется. Никто не говорит
«неверно»: проверяет железо.

**Почему здесь не сработает ИИ.** Условия выдаются по шагам, следующий
шаг зависит от данных, которые видны только в своей базе, а данные ИИ не
видит. Попросить ИИ «написать запрос с LIKE» можно — но код замка он не
назовёт.

**Подсказки.** Конверт с подсказкой можно открыть в любой момент —
команда стоит минуту у «стойки регистрации». Чтобы ни одна команда не
застряла насовсем, у преподавателя есть подсказка последнего уровня —
готовое условие для шага.

## 7. Что видит комиссия

* Методический приём, которого не было: **«воплощённое» выполнение
  запроса** (студенты — строки) и **физическая самопроверка** (замок).
* Переход от конкретного к абстрактному прямо на уроке: 30 строк людьми →
  20 000 строк машиной; необходимость SQL выводится, а не объявляется.
* Ошибки предупреждаются, а не разбираются задним числом: скобки и NULL
  студенты «прожили» раньше, чем встретили в квесте.
* Каждый студент активен все 90 минут: в живой части он строка, в
  квесте — член команды.
* Гости — участники, а не наблюдатели.
* ДЗ выдаётся в форме, которую запомнят (посадочный талон из ящика).

## 8. Что может пойти не так

| Риск | Что заранее делаем |
|---|---|
| Часть группы не пришла | Карточки отсутствующих лежат на пустых стульях: «строка есть, человека нет». Преподаватель поднимает карточку, если она попадает в результат. |
| Студенты стесняются вставать | Первый запрос — `WHERE` по полю, под которое подходят почти все: встают вместе, неловкости нет. |
| Шум и беготня | Шеренга строится у доски по сигналу; на «живую» часть отведено ровно 34 минуты. |
| Команда не успевает | Цепочка из 4 шагов, но код можно собрать и после 3-го (рецепт в конверте даёт запасной вариант). Подсказки. |
| Замок «не открывается» при верном коде | Коды проверены накануне трижды; у преподавателя записаны все коды и запасной ключ от ящика. |
| Компьютер или СУБД не работает | Большая таблица заранее загружена на каждый компьютер; на одном компьютере команды — достаточно. |

## 9. Подготовка (за неделю)

1. Сгенерировать данные: 30 «живых» строк (под карточки) + 20 000 строк
   большой таблицы с четырьмя «пропавшими» пассажирами, подобранными так,
   чтобы ловушки скобок и NULL срабатывали.
2. Свёрстать и распечатать карточки, конверты квеста, посадочные талоны.
3. Купить ящик, блокиратор, четыре кодовых замка; выставить коды по
   ответам.
4. Загрузить базу на компьютеры аудитории; прогнать квест самому от
   начала до конца с секундомером.
5. Слайды: только запросы крупно (по одному на слайд) — экран здесь
   вторичен.
